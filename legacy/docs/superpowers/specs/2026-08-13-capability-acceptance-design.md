# 真机能力验收模式设计

日期：2026-08-13
依据：根目录 `项目最终目标.md`
状态：用户已于 2026-08-13 明确同意

## 目标

为尚无真实证据的通用底层动作提供一条受监督的真机验收与能力晋级路径。验收模式复用 DeepSeek 动态任务图、Qwen 真实画面观察、本地单动作控制器、动作后四帧验证和按 `device_id` 隔离的硬件租约，不增加任何 App 专用流程。

首批需要验收的能力是 `input_verified_text`、`long_press` 和 `drag`。设计本身按动作类型工作，后续新增通用底层动作时不需要新增 App 或命令分支。

## 不做什么

- 不因模型返回成功就自动修改设备能力。
- 不让正式产品控制器临时获得未验收动作。
- 不允许一份报告一次启用多个动作或多个设备。
- 不用模拟器、离线截图或模型测试替代真机报告。
- 不在活动会话占用设备时启动验收，也不热更新运行中的控制器。
- 不为微信、抖音、浏览器或某个页面写验收步骤。

## 架构

新增独立的 `CapabilityAcceptanceManager`。它创建一套验收专用的 `UniversalAgentOrchestrator`，但共享正式运行时的 DeepSeek、Qwen、`DeviceTaskRegistry` 和设备级物理租约。

验收编排器只在内存中创建一个临时 `RobotController`：其能力集合等于设备当前已验证能力加上本次唯一候选动作。临时控制器不会写入 `DeviceControllerRegistry`，不会进入正式网页主路径，也不会在服务重启后保留。

验收仍然走唯一执行循环：

```text
验收目标 + device_id + candidate_action
  → DeepSeek 高层任务图
  → Qwen 当前唯一动作
  → 本地检查动作必须等于 candidate_action
  → 展示完整风险/动作确认范围
  → 用户确认后执行最多一个物理动作
  → 四帧重新观察与控制器验证
  → 生成不可变 acceptance_report.json
  → 用户再次确认启用
  → 原子更新 device_registry.json
  → 等待安全重启后生效
```

## 验收会话

每个验收会话有独立 `trial_id` 和证据目录。会话必须记录：

- `trial_id`、`session_id`、`task_id`、`device_id` 和候选动作；
- DeepSeek revision、当前 subgoal、风险 ID；
- 确认前 `observation_id`、`fingerprint` 和四帧路径；
- Qwen 的唯一动作、可信候选和本地控制器判定；
- 物理动作数、动作后 `observation_id`、`fingerprint` 和四帧路径；
- `action_outcome`、验证错误、模型请求 ID 和当前 Git 提交；
- 报告状态和未生效/已晋级状态。

启动阶段必须满足：

1. 候选动作属于通用物理动作集合且当前尚未验证；
2. 同一设备没有正式任务或其他验收会话；
3. 设备控制端、摄像头、标定和共享租约可用；
4. DeepSeek/Qwen 只产生一个动作，且动作类型与候选动作完全一致；
5. 启动和风险确认阶段物理动作数始终为零。

如果 Qwen 提出不同动作，验收会话安全停止，不允许通过临时能力集合顺带执行其他动作。

## 两次确认

第一次确认是现有的精确动作确认，必须绑定：

`trial/session/task/device/revision/subgoal/risk/observation/fingerprint/action`

确认前重新拍摄并重绑定目标，任何设备、任务图、画面、语义目标、状态或区域漂移都会消费并作废确认，物理动作数保持零。

第二次确认只负责能力晋级，必须绑定：

`trial/report/device/action/report_sha256/registry_sha256`

晋级确认不能执行机械臂，也不能复用动作确认。报告或注册表在确认后发生变化时，晋级失败并消费该确认。

## 通过标准

验收报告只有同时满足以下条件才标记为 `passed`：

- 本次确认只产生一个物理动作；
- `resolved_action.kind` 与候选动作完全一致；
- 动作前后均有四张可读取的 JPEG 证据；
- 动作后 observation ID 已变化；非等待动作 fingerprint 已变化；
- `action_outcome=matched`，没有观察或验证错误；
- 证据和报告均位于本次 trial 目录内；
- 设备、会话和确认范围没有串线；
- 当前代码提交被记录。

任何失败仍保存报告和已产生的真实证据，但 `passed=false`，不能晋级，也不能自动重试机械臂。

## 原子晋级与回滚

`CapabilityRegistryPromoter` 在进程锁和操作系统文件锁下执行以下步骤：

1. 读取并严格校验 `device_registry.json` v1；
2. 校验 report SHA-256、设备、动作、证据路径和 `passed=true`；
3. 校验动作仍未启用且注册表 SHA-256 与确认范围一致；
4. 把原注册表保存到 trial 目录的 `registry_before.json`；
5. 在同目录创建临时文件，写入、flush、fsync 后通过 `os.replace` 原子替换；
6. 写入 `promotion.json`，包含前后摘要、时间和 `requires_restart=true`；
7. 消费晋级确认，禁止重放。

晋级只修改一个设备的一项动作。运行中的 `DeviceControllerRegistry` 不热更新；网页显示“已写入配置，等待安全重启”。回滚使用 trial 目录中的原始注册表，并同样经过原子替换。

## 网页控制台

在现有控制台底部增加“真机能力验收”面板：

- 显示所选设备当前已验证和待验收动作；
- 输入通用验收目标并选择一个动作；
- “生成验收计划”只规划和观察，明确显示物理动作数 0；
- 风险确认和动作确认复用现有作用域显示规则；
- 动作完成后显示报告、八张前后证据和通过/失败原因；
- 只有 `passed=true` 时出现“确认启用该能力”；
- 晋级后显示“等待安全重启”，不自动重启服务。

验收面板不提供连续执行按钮，不允许选择已验证动作，不允许同时存在两个设备相同的验收会话。

## 错误与并发边界

- 正式任务占用设备：在建目录、相机和模型调用前返回 409。
- 另一进程持有设备租约：返回 409，并显示活动 owner 元数据。
- 报告、证据或注册表摘要不一致：消费晋级确认并失败关闭。
- 进程在写注册表时崩溃：旧文件或完整新文件二选一，不留下半写 JSON。
- 动作已执行但动作后观察失败：记录 `physical_actions=1` 和已有证据，报告失败，禁止重试和晋级。
- 服务重启：未完成 trial 可只读恢复；一次性动作确认和晋级确认均不跨进程恢复。

## 测试策略

1. 纯单元测试验证报告构造、路径约束、摘要、一次性确认和原子替换。
2. 模拟编排器测试验证零动作启动、候选动作不一致、一次动作、动作后失败和设备互斥。
3. FastAPI 测试验证所有请求严格字段、控制令牌、409 失败结构和不热更新。
4. 前端协议及浏览器契约验证验收面板没有自动动作、显示完整范围、晋级按钮只在通过后出现。
5. 真机验收分别记录输入、长按、拖动；代码测试结果与真实报告分开呈现。

## 设计自检

- 通用性：按动作和设备工作，不包含 App 名称或固定页面步骤。
- 职责边界：DeepSeek 规划、Qwen 观察、控制器校验、机械臂执行和本地晋级互不替代。
- 一次一动作：验收确认只授权一个候选动作，失败不重试。
- 真实证据：只有真机前后帧和一个物理动作可以产生可晋级报告。
- 多设备：所有 trial、租约、证据和晋级都绑定 `device_id`。
- 可恢复：注册表更新原子化且保留原始快照，运行服务不热更新。
