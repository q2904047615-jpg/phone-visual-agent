# 项目运行机制与 Open-AutoGLM 对比报告

日期：2026-09-05，Asia/Shanghai。对象：当前工作树，包括尚未提交的修改；不能仅用 Git HEAD 代表本报告所检查的代码。

本报告是源码审查与运行记录说明，不是新的运行规则。本轮没有修改生产代码、重载服务、提交手机任务、操作卖家程序或调用 DeepSeek/Qwen。外部对照为本轮读取的 Open-AutoGLM 官方 main 分支，重点比较 Android ADB 主路径，未对两个项目做同设备成功率实验。

## 一、先给结论

1. 你的项目确实实现了“DeepSeek 初次规划 → Qwen 看图并选一步 → 本地绑定与执行 → 新截图”的主链，不是每一步都由 DeepSeek 和 Qwen 轮流审批。
2. Qwen 不只是识别器。它同时负责当前画面事实、当前子目标下一动作、点击点以及当前子目标是否完成。这符合当前项目目标，但比“只识别画面”承担更多职责。
3. 正常主链传给 Qwen 的是当前子目标投影，不是完整计划和持续累积的聊天历史；它仍会收到相关对象、输入正文、约束、效果及执行回执上下文。
4. 本地并非只检查坐标。代码中仍有精确输入正文、App 直启身份、导航栏状态、效果画面变化、重复动作与资源预算等检查。此前若把它概括为“其他完全交给 Qwen，本地不再判断”，是不准确的。
5. Open-AutoGLM 的 Android 主路径更短，直接读取手机截图、通过 ADB 执行动作；你的项目主要从相机取得画面、通过机械臂操作。这不是换一套提示词就能消除的差异。
6. 当前代码有完整自动回归通过的记录，但尚未证明当前版本可以稳定完成完整真机任务。最近一次设备核对卡在相机采集，尚未进入 Qwen 判断。

可行性结论：当前通用架构属于“有条件可行”，条件包括可靠画面、正确计划、可执行的模型输出和实际设备效果；当前版本的完整真机能力仍“尚未验证”。不能据此保证所有任务能跑通，也不能把所有失败归因于 Qwen。

## 二、你在网页输入任务之后，实际发生什么

假设输入：

> 打开微信，打开文件传输助手，发送 aaazjie？你好。

以下是解释性示例，不是本轮真实模型输出，也不是代码中写死的微信流程。

### 1. 网页/API 接收任务

正式自然任务入口是 `POST /api/agent/generic-supervised/start`，默认开启自动推进。入口检查请求格式、任务长度、控制来源、设备及任务占用等条件，再建立本次会话。

普通发送、删除、输入不应仅因改变外部状态而让用户逐次批准。产品约定需要明确确认的是登录/身份认证和付款/资金交易。运行时出现的 `awaiting_confirmation` 还可能只是单动作执行凭据的内部等待状态，自动循环会消费它，不能一看到这个词就解释成“需要用户确认”。

源码：[请求定义](C:/Users/Administrator/Documents/Claude/Projects/手机自动点击器/poc/web_app.py:174)、[自然任务入口](C:/Users/Administrator/Documents/Claude/Projects/手机自动点击器/poc/web_app.py:1285)。

### 2. DeepSeek 把整件事整理为有序目标

它可能产生“微信在前台 → 目标会话打开 → 正文输入完成 → 消息发送完成”等高层目标。每个高层目标可以包含多次观察和动作，不是一目标只许点击一次。

它还整理：操作对象、收件人、正文、约束、完成条件、输入字段与操作类型、哪些子目标对应真正的发送等效果。

例如“打开文件传输助手”是目标，不应被写死为“点某固定坐标，再点另一个固定坐标”。具体怎么进入，应由 Qwen 根据当时页面决定。

### 3. 本地选择当前目标，签发本轮动作集合

本地派生唯一运行状态，确定当前子目标。根据设备支持能力、输入操作类型和明确指定的动作合同，生成本轮允许的动作集合。

例如当前只是导航时，不开放正文输入动作；当前是输入事务时，才开放对应输入动作。只有用户或正式协议已经唯一指定动作，才使用 `required_action_kind` 限定动作，不能靠目标文字猜测并强制限定。

这个集合先于模型请求签发，后续模型、绑定和执行消费同一份。动作集合统一，并不等于所有动作之后都不再检查其他条件。

### 4. 相机取得当前画面，Qwen 选一个动作或报告完成

本地先采集并检查多帧。普通观察选一张较清晰的稳定帧；输入相关观察把尾部三张稳定帧一起发给 Qwen，以便识别闪烁光标等当前事实。

如果此刻已经在目标聊天页面，导航目标可以直接完成，不必先退出再进入。如果当前目标是发送新消息，旧聊天气泡不能单独证明本次发送已经发生。

### 5. 本地绑定动作，执行前再确认画面没有失效

Qwen 选出的动作必须绑定当前任务、设备、子目标、观察及画面指纹。点按使用它同次响应给出的目标身份和点击点。

执行前还会本地重新取图核对，而不是不加检查地执行几十秒前的旧坐标。此处本地取图不是又让 DeepSeek 或 Qwen 审批一次。

### 6. 设备只执行这一个动作，再取新图

一般点按、Home、返回、滑动走机械设备；当前配置的文字输入/清空走 ADB Keyboard；批准且存在可信映射的 App 可以直启。

动作后等待并重新采图，再由一次 Qwen 响应同时给出新页面事实和下一动作/完成判断。本地还会核对必要后置条件。

### 7. 当前子目标完成，才进入下一个目标

`matched` 表示本地对刚才动作的相应验证通过，不是整个任务完成；其证明力度取决于动作类型。普通点击的稳定新图不等于“语义目标已经达到”。

当前截图中 Qwen 发布 `finish`，且本地相关完成条件检查通过，才推进目标。切换到下一目标后需要新的观察，不能把上一个目标的旧观察直接改名用于下一目标。

所有目标完成才是整件任务结束。达到循环预算、采图失败、动作匹配后又失败，均不能算整件任务成功。

### 8. 你批准的后台清理规则是一个明确例外

清理后台卡片采用“先确认主屏幕 → 打开最近任务并确认后台页 → 找到并点击系统一键清理按钮”的固定状态顺序；已经在主屏幕时不需要重复 Home。按钮不在当前可见区域时允许上下滚动寻找，不再滑走某个任务卡片；目前允许同时清掉其他可清理后台。

这个顺序只应适用于清理后台，不应推广为每次打开 App、查看后台或切换 App 都先清理。每步仍用新图找当前控件，不是固定屏幕坐标。现有部分后台页面级限制可能超出这个适用范围，见第十节。

## 三、DeepSeek：做什么，具体怎么做

### 它收到什么

用户完整任务文本，加初始规划提示词和结构化输出要求；这一环节不传手机截图，不要求它看图找点击位置。

### 它输出什么

- 总体目标与对象：App、收件人、正文等。
- 约束与正向完成条件。
- 有序子目标及依赖关系。
- 效果意图及其所属子目标：区分“准备文字”和“真正发送”。
- 输入任务所需字段/操作声明；有充分依据时声明唯一动作类型。

它不输出当前运行指针、实际完成证据、机械坐标或任意 Shell。任务/设备身份和运行状态由本地建立并检查。

源码：[规划实现](C:/Users/Administrator/Documents/Claude/Projects/手机自动点击器/poc/agent/application/deepseek_task_graph.py:33)、[初始提示词](C:/Users/Administrator/Documents/Claude/Projects/手机自动点击器/poc/agent/application/prompts/deepseek_initial.txt)、[输出 schema](C:/Users/Administrator/Documents/Claude/Projects/手机自动点击器/poc/agent/application/prompts/deepseek_schema.txt)。

### 调用次数与错误边界

正常是一次逻辑规划，随后退出运行循环，不参加动作后重规划。供应商网络层对部分瞬时故障最多尝试三次；这是传输重试，不是让三个模型方案互相投票。

本地检查计划字段、引用和依赖是否成立，但结构合法不能证明语义理解正确。例如收件人理解错、漏掉一个目标、将准备动作错归为效果，都可能给后续带来困难。不能因为最后在 Qwen 阶段停住，就认定最初计划一定正确。

按最新加载记录，配置模型为 `deepseek-v4-flash`，thinking 关闭。配置成功不证明任务理解必然正确。

## 四、Qwen：它实际知道什么，承担什么责任

### 1. 正常主链不是把整张计划都交给它

发送给模型的主要内容是：当前子目标、完成条件、约束、相关对象和正文、当前效果要求/禁止提前发生的效果、必要的输入事务与前序执行信息、本轮动作集合、当前图片及输出合同。

代码虽然在本地保留原始任务上下文，但 `ActiveVisualGoal.observation_context` 在有效当前子目标存在时，只输出该子目标投影。没有有效当前子目标的上下文仍存在 root 回退，不能宣称所有辅助入口都绝不可能使用根上下文；正常通用会话应走当前目标分支。

它也不是完全不知道任务背景。例如正在输入时，必须知道要输入哪段正文，发送阶段必须知道对象和效果要求。

源码：[当前目标构造](C:/Users/Administrator/Documents/Claude/Projects/手机自动点击器/poc/agent/application/universal_agent_orchestrator.py:286)、[发送上下文选择](C:/Users/Administrator/Documents/Claude/Projects/手机自动点击器/poc/agent/domain/generic_goal.py:56)。

### 2. 一次请求内同时做三件事

| 内容 | 通俗含义 | 谁负责 |
| --- | --- | --- |
| `scene` | 当前是什么页面、有哪些相关事实 | Qwen 识别，本地解析 |
| `input_structure` | 相关输入框的正文、聚焦、预编辑等事实 | Qwen 识别，本地投影 |
| `decision` | 当前只做哪个动作，或者当前目标已经完成 | Qwen 选择，本地绑定 |

因此它既看图，也做当前目标内的单步决策；不是仅把识别框交给 DeepSeek 再决定点击什么。

用于绑定的 `QwenVisualDecisionObserver` 消费上述同一响应，不会因为名字又带 Qwen 就额外远程调用一次模型。

正常每次观察一次 Qwen 请求，目前该观察请求最多一次尝试、超时约 60 秒、输出预算 5200 token。切换目标、动作后观察和有界只读纠正会增加观察次数，所以总调用数不严格等于物理动作数。

源码：[观察请求](C:/Users/Administrator/Documents/Claude/Projects/手机自动点击器/poc/agent/infrastructure/generic_scene_observer.py:228)、[单步绑定](C:/Users/Administrator/Documents/Claude/Projects/手机自动点击器/poc/agent/application/qwen_visual_decision.py)。

### 3. 输入框判断现在怎么工作

正文的视觉来源是 `input_structure.application_inputs[*].text`。聚焦来源是同结构中的 `focused=true/false/null`，不是键盘有没有显示，也不是历史上有没有点击过。

当前合同要求：有直接正向焦点证据才报告 true；另一字段聚焦等明确反向证据报告 false；不能确定时为 null。三张稳定帧供同一次判断，允许光标只在其中一张出现。

本地不会把“ADB Keyboard 显示 AI 输入中”“键盘不可见”“以前点过输入框”强行改成聚焦 true。非空输入/清空文字动作要求绑定本轮 focused=true 的字段。

这会产生一个实际停点：肉眼觉得输入框可用，但模型连续不能从相机画面确认聚焦，输入链仍可能停住。多帧改善了证据，不等于彻底消除了焦点识别不一致。

已经为空的清空目标可以直接完成，不要求先聚焦再发送一次空清空；独立聚焦目标也可以用当前明确聚焦事实完成。

### 4. 点击点怎么来

点按分支以同一响应中的 `decision.target` 表示目标身份，以 `tap_point` 表示唯一点击点。不再由本地取粗元素框中心，也不通过 OCR 或颜色分割纠正这个点。点按响应若附带非权威元素列表，入口会排除它对执行的影响。

坐标按请求图片的明确坐标空间转换，再经过机械标定，不等于直接把模型数字原封不动发给机械臂。宽度为 1000 的请求坐标网格还带对应图片高度，不能未经换算照搬另一项目的双轴 0–1000 数字。

坐标合法只能证明可解释、可达，不能证明模型选中的那个点语义正确，也不能证明机械触点真的碰到了手机。

### 5. 它的错误不止一种

可能是看错正文或焦点、选错对象、给错位置、动作与目标不一致、提前完成，也可能只是 JSON/字段不满足合同。另一些所谓“Qwen 错误”实际上发生在模型调用前的采图阶段或调用后的本地校验阶段。

当前 Qwen 配置为 `qwen3.7-plus`，由阿里云通道调用，thinking 关闭。它和 Open-AutoGLM 默认使用的手机操作模型并非同一个模型；没有同条件实验，不能直接断言谁的成功率更高。

## 五、本地代码到底还检查哪些东西

### 1. canonical 解析与绑定

canonical 可以理解为项目内部统一动作名和字段合同。它把模型输出转换成唯一可执行动作，并检查：

- 输出类型及动作字段组合能否解释。
- 动作是否在本轮已签发集合内。
- 目标、输入字段和点位是否来自当前响应、是否能唯一绑定。
- 当前效果是否允许发生，是否错误提前执行未来效果。
- `finish` 是否满足输入/效果的当前事务要求。

它不是另一个视觉模型，不能通过类型检查识破所有语义误判。

### 2. Controller 与执行器

主要检查设备、观察指纹、坐标、机械可达性、执行凭据以及动作后结果。凭据在执行时一次性消费，不能拿旧坐标和旧凭据无限重放。

但源码还有这些后置检查，必须如实保留在说明中：

| 现有检查 | 实际作用 | 能否与 Qwen 的完成意见不一致 |
| --- | --- | --- |
| 精确输入正文/预编辑检查 | 将 Qwen 报告的新正文与本地预期比较 | 能，模型说完成也可能被拒绝 |
| `launch_app` 后 App 身份检查 | 要求新图中的 App 身份匹配可信目标 | 能，身份字段不匹配可停止 |
| 导航栏显露后检查 | 要求结构化导航栏可见 | 能，字段缺失可停止 |
| 部分效果完成前的像素变化门 | 排除无明显画面变化的效果完成 | 能，小变化可能不足；大变化也不等于业务成功 |
| 动作后稳定性检查 | 新画面不能仍处于不可用变化状态 | 能，页面动画/闪烁可能影响 |

这些比较有的消费 Qwen 的事实，有的是本地图像计算；并不全是重复调用模型，但它们确实能影响任务继续。因此“只有 Qwen 一个判断点”不是当前完整运行事实。

### 3. 为什么新任务不能被旧气泡完成

初始截图是本次任务的起始状态，不是本次已经执行过的证据。输入、发送等目标需要本次相应动作/效果的执行记录与新图，不能只见到历史同文气泡就跳过。

但是记录只证明执行请求及其归属；新气泡是否确实出现、是否属于正确会话，仍依赖画面判断。防旧记录复用解决的是一类错误，不是保证视觉理解永不出错。

对“已经在目标页面”“输入框本来就空”等结果型目标，可以零动作完成。这与“必须新发送一条消息”的效果型目标不同。

## 六、机械臂与 ADB Keyboard 分别做什么

### 机械执行

模型视觉点 → 图片坐标换算 → 机械标定映射 → 控制端执行 → 手机实际接触 → 新相机画面。

这条链包含识别偏差、拍摄透视、标定误差、触点高度、接触持续性、控制端响应和手机响应等可能失败环节。仅凭控制端命令成功或手机画面没变，不能唯一定位为“机械没碰到”；也可能是点位、对象、页面状态或拍摄问题。

### 当前 ADB Keyboard 路径

固定可信设备/可执行文件/IME检查 → 当前输入事务绑定 → UTF-8 文本 Base64 编码 → `ADB_INPUT_B64`；清空使用独立的 `ADB_CLEAR_TEXT`。

广播成功返回不代表正确输入框已收到正确文字，所以之后仍有相机新图和正文核对。输入连接错误、焦点丢失、IME 不对、无线断线或广播结果不确定，均可能失败。

本项目的 append 不隐式清空；如果需要先清理已有草稿，应作为清空动作完成并观察，再输入。正式路径不在每次输入时切换并恢复输入法，不回退 Companion IME，也不在失败后自动改通道重输。

ADB Keyboard 不负责识别收件人、点击输入框、判断消息是否发送。它与机械臂、相机是不同通道：“ADB 已连接”不等于“整个 Agent 已就绪”。

## 七、与 Open-AutoGLM 的关键区别

以下仅比较官方 Android ADB 主路径，不代表所有分支、第三方改版或实际部署。

| 维度 | 你的当前项目 | Open-AutoGLM Android 主路径 |
| --- | --- | --- |
| 规划 | DeepSeek 首次建立目标定义，之后退出 | 一个视觉模型在主循环中持续决策 |
| 上下文 | 当前目标投影、必要实体与回执 | 完整初始任务及累计文字/动作历史 |
| 画面 | 外部相机，多帧检查，普通单图/输入三图 | ADB 屏幕截图 |
| 当前 App | 主要从视觉事实识别 | 可通过 ADB 系统信息读取 |
| 模型输出 | scene、输入事实、单个 canonical 动作/finish | do/finish 风格动作指令 |
| 点按/滑动 | 模型点位经机械标定后执行 | 模型坐标换成屏幕像素，由 ADB 执行 |
| 输入 | 预先配置 IME、独立清空/追加、事务与新图验证 | Type 内包含切换输入法、清空、输入、恢复 |
| 完成与恢复 | 当前目标 finish 加事务/后置条件；有界纠正 | 模型持续观察决策，循环有步数上限 |

### 为什么它看起来更容易连续跑

从架构可以推断：直接数字截图避免一部分反光、透视与外部采集问题；ADB 坐标输入避免机械接触和标定误差；较少的结构化中间合同减少本地拒绝机会。这里是机制分析，不是测得它比你的项目高多少成功率。

模型也不同。官方提供面向手机操作的 AutoGLM 模型方案，不能把演示成功全归功于 ADB Keyboard。依据：[官方项目说明](https://github.com/zai-org/Open-AutoGLM)、[模型客户端](https://github.com/zai-org/Open-AutoGLM/blob/main/phone_agent/model/client.py)。

它不是没有规则：提示词同样指导先聚焦再输入、处理加载、纠正失败和人工接管等。依据：[官方提示词](https://github.com/zai-org/Open-AutoGLM/blob/main/phone_agent/config/prompts.py)。

还要注意“结束”口径：主循环部分解析异常会转成 finish，达到结束条件并不自动证明手机业务成功。因此比较时必须看手机结果，不能只比较有没有异常或是否打印完成。依据：[官方主循环异常处理](https://github.com/zai-org/Open-AutoGLM/blob/main/phone_agent/agent.py)。

官方 issue 中也有坐标偏移/解析失败及输入法切换问题报告，说明它并非所有环境都能直接跑通；这些是他人的问题报告，不是本轮复现，也不能据此断言当前版本尚未修复：[issue 34](https://github.com/zai-org/Open-AutoGLM/issues/34)、[issue 130](https://github.com/zai-org/Open-AutoGLM/issues/130)。

### 为什么不能说“已经完全照搬了它”

你借用了 ADB Keyboard 的文字广播机制，也采用了模型直接点位思路；但拍摄、机械执行、规划、输入事务和完成检查仍是你的项目实现。

若把截图、点击、Home 等都改成它的 ADB 路径，会改变已批准的“机械执行为主、ADB 仅限文字和可信直启”边界。那是产品方案变更，不是修一个输入法函数即可完成。本轮不实施这种变更。

## 八、遇到哪些情况会报错、暂停或停止

下面按运行阶段覆盖主要失败家族，不把所有异常都叫 Qwen 错误，也不把未来所有未知缺陷假装列举完毕。

| 阶段 | 典型触发条件 | 正确归因或解释 |
| --- | --- | --- |
| 网页/API | 空任务、超过当前 500 字符限制、请求字段不符、控制来源/token不符 | 请求/入口问题；合法长任务被限还需审查容量设计 |
| Agent 调用 API | 用错路径、方法或请求体导致 404/405/422 | 调用方命令错误，不是 Qwen 或设备失败 |
| DeepSeek 网络 | 未配置、认证失败、额度/限流、网络超时 | 模型服务/配置问题 |
| DeepSeek 计划 | JSON无效、引用/依赖错误、缺字段、输入操作合同不成立 | 模型合同输出或解析实现问题；需看原始输出区分 |
| 初始计划语义 | 漏目标、错对象、错约束/效果归属 | 即使结构通过，也可能带偏后续；不能只查 Qwen |
| 设备占用 | 同机另一个任务占用、设备选择或租约不一致 | 运行状态/控制权故障 |
| 采图 | 相机取不到真实帧、尺寸不符、占位图、不稳定/不清晰 | 观察链故障；可能尚未调用 Qwen |
| Qwen 网络 | 认证、限流、超时、输出被截断 | 服务或资源问题，不等于看不懂图 |
| Qwen 输出合同 | JSON/动作字段组合不合法、必需对象无法唯一绑定 | 合同输出或代码边界；先保存原始响应分类 |
| Qwen 视觉/决策 | 错字段、错正文、焦点 unknown、点错位置、提前完成 | 模型视觉/决策问题，但需排除坏图与错误目标 |
| 本地动作集合 | 设备不支持、当前输入操作不允许、required_action不匹配 | 能力/合同问题；错误裁剪属于代码缺陷 |
| 执行凭据 | 旧观察、错误设备、指纹变化、凭据已消费 | 不能继续执行当前旧动作，不代表整件目标不合法 |
| 几何与机械 | 坐标越界、缺标定、方向或可达性不成立 | 几何/执行故障；经验阈值是否过严需另证 |
| 输入执行前 | 非空文字动作没有同帧 focused=true、字段不唯一 | 输入绑定停点，不能凭历史点击补成聚焦 |
| ADB 输入 | 无线设备断线、IME不符、广播拒绝/超时或结果不确定 | 文字 transport 故障；不得假装输入成功 |
| 动作执行后 | 取不到新图、页面持续变化、预期正文不符 | 动作可能已经发生，必须报告动作数及未知效果 |
| 本地后置门 | App 身份/导航栏事实不满足，效果像素变化不足 | 本地规则停止，不应写成 Qwen 普通 blocked |
| 提前或重复效果 | 未到发送目标先发送；已执行效果又要求再执行 | 效果归属或重复执行风险，不能自动重发 |
| 纠正次数 | 重复聚焦、重复系统导航、相似元素滑动到限 | 当前有界恢复策略停止；不证明任务客观无法完成 |
| 循环预算 | 一次自动推进默认 12 动作/24 迭代到限 | 自动暂停/预算耗尽，不是成功；长任务可能仍有后续 |
| 文件与资源 | 证据目录、原子写入、磁盘或资源释放失败 | 本地存储/实现故障；非核心诊断不应升级成业务否决 |
| 登录或付款 | 进入相应明确确认环节 | 产品要求的确认，不是程序报错 |

同样要区分“动作前拒绝，0 动作”和“动作已发生但后图验证失败”。尤其输入、发送失败，后者不能直接重跑，否则可能重复文字或重复消息。

## 九、为什么你感觉修完这里，又在那里停住

### 已确认的结构原因

第一，失败点分布在整条链上。DeepSeek、Qwen、本地、相机、机械、ADB 任一必要环节不满足，任务都无法完成。修好其中一个并不自动覆盖其他环节。

第二，Qwen 承担多份事实和动作合同。本地不是只接受一个坐标，还要消费页面、输入、效果等信息。模型可以看懂大部分内容，但某个必要字段不成立仍会停。

第三，仍有本地后置判断。删除了重复焦点推导、重复动作裁剪等，并不意味着整个项目已没有其他可能冲突的检查。当前源码不能支持“旧规则已全部删除、只剩一个判断”的绝对说法。

第四，离线样本不能覆盖真实相机和手机状态。测试通常能覆盖给定响应和边界，不能自动证明真实模型在光标闪烁、反光、遮挡、旧草稿、网络变化下都稳定。

第五，加载成功和设备可用是两件事。窗口在线、ADB在线、API在线分别只说明一部分链路，必须另看真实帧和任务结果。

### DDD 为什么没有防住这些问题

当前项目仍采用渐进式 DDD 模块化单体：接口层收任务，应用层编排，领域层表达动作/状态规则，基础设施层连接模型和设备。

DDD 能帮助分清职责、依赖和状态归属，但不会替你证明提示词正确、坐标可达、焦点识别稳定或规则互不冲突。把一个过严条件放进领域层，它仍然是过严条件；把模型输出解析分成多个文件，也不会自动提升真机成功率。

所以问题不在于“用了 DDD 为什么还会错”，而在于“具体合同、实现、恢复和验收是否与产品目标一致”。

## 十、目前还有哪些已发现但不能称为已修完的地方

以下先区分：分支存在有源码证据；其所有真实误拒绝情形并未在本轮逐个复现。

1. App 直启身份、导航栏显露仍有 Controller 后置否决。与“本地只验执行、不再另判页面语义”的简化口径存在差距。
2. 后台页的部分滑动限制按页面生效，应检查是否超出了用户“只在清理卡片时固定顺序”的范围。
3. 未来效果纠正时，代码会从下一轮动作集合去掉该动作类型，而不只是那个错误目标；如果去掉的是整个 `tap_semantic`，可能连合法导航点击一起排除。分支可见，不等于本轮已经复现特定任务失败。
4. 任务长度、正文容量、字段数、compact 元素预算等是工程限制，不代表超限任务天然不合法。
5. 多帧稳定性、清晰度、手势距离、像素变化等固定阈值，没有覆盖所有分辨率/光照/小幅真实变化的普适证据。
6. 一次自动推进预算和提示词预算，可能截断本来可以继续的长任务。

这些不是本轮新加的限制，也不是现在额外阻断任务的理由；同样不能在没有反例验证前宣布“全删掉一定更好”。本轮仅报告，不叠加生产补丁。

## 十二、我对项目现状的最终判断

你的项目不是没有执行主链，也不是单纯“Qwen 不行”。它是一条真实存在、比 Open-AutoGLM Android 主路径更长的链，当前同时承受外部相机/机械的不确定性、模型输出的不确定性和本地规则的约束。

此前修复如果只针对最后一个报错，让单个样本通过，再把“相关测试通过”说成“整条任务已经修好”，这个结论就是超出了证据。正确的责任划分不是每次把最终停点归给 Qwen，而是保留最早失败位置、模型原始输出、动作前后图、动作回执和实际终态，定位本轮究竟在哪里中断。

后续优先事项应是：先确认当前真实画面采集恢复，再用已批准的完整任务建立一条可审计的同会话运行证据；在此前，不用新提示词或新业务规则掩盖采图故障。对于上述剩余本地检查，用离线正向/变化反例确定是否误拒绝，再决定统一移除或收敛。

本轮交付边界：完成运行机制与源码对比报告；未修复上述问题，未证明当前真机任务已经跑通。
