# 多设备调度准备核对（2026-10-14）

## 结论

结论：**有条件可行，尚未完成多设备真机调度验收**。

平台的逻辑设备隔离已经存在并通过离线合同测试：会话、跨进程租约、fencing epoch、设备锁和相机/运行资源均按 `device_id` 管理；同一卖家控制窗口的不同机位复用共享物理操作锁，避免两个任务同时驱动同一机械臂。本轮新增只读 GA readiness 评估器和虚拟双设备测试，把“离线合同通过”和“真实多设备可用”分成两个状态。

当前生产配置不能安全进入多机位物理调度：注册表共列出 10 个设备，但只有 `device-local-01` 启用；`device-local-02` 至 `device-local-10` 均为 `enabled=false`。本工作树只找到 `poc/tap_calibration.json`，没有 2–10 号机位的真实校准文件。根据《项目交接文档》既有停止条件，不能复制 1 号绝对坐标、不能启用未校准设备、不能实现未经真实机位证据支持的切位点击。

## 已验证的逻辑合同

- `DeviceTaskRegistry` 为每个 `device_id` 保持活动会话、进程租约、fencing epoch 和可重入设备锁。
- 相同设备的并发会话被拒绝；不同设备可以分别持有租约。
- `DeviceControllerRegistry` 为每个启用设备解析独立 controller/calibration；共享控制窗口只共享 operation/capture lock，并要求不同 `machine_position`。
- `DeviceRuntimeResourceRegistry` 为每个 `device_id` 提供独立协调锁和相机协调器。
- 选取的 3 项聚焦测试通过：同线程设备锁可重入、释放后 fencing epoch 递增、当前真实设备能力注册读取通过。

设备注册/共享窗口/临时配置测试已在项目 Python 3.12 环境重跑通过 `20/20`；新增 GA readiness 测试 `3/3`。这些均为离线或虚拟配置证据，不计为真实多设备验收。

## 进入物理多设备调度的前置条件

1. 为每个要启用的设备提供真实、独立的机位校准文件，并记录对应 `device_id`、`machine_position`、控制窗口和验证动作。
2. 在不复制绝对坐标的前提下，逐设备完成 controller/camera/ADB 所需的就绪核对。
3. 先做两设备离线互斥/并存合同回归，再做一次真实的不同设备样本；共享机械臂时仍按共享物理锁串行，只有真正独立的物理执行器才允许并行。
4. 每启用一个设备后重新加载服务，核对 `/api/status`、`/api/doctor/{device_id}`、活动任务和租约状态，再进行单动作、动作后新观察的验收。

在这些证据到齐前，多设备调度阶段保持未开始状态；不会修改生产注册表，也不会让 2–10 号设备进入运行路径。
